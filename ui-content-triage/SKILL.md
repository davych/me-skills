# UI 内容分级呈现

GPT 类模型拿到内容后最常犯的错：不判断就渲染——列表再长也全列出来，API 原始返回直接转成大段文字，所有字段同等字号铺开，没有主次，也不管用户当下到底要浏览、查找、比较还是按步骤完成。本 skill 要求先停下来判断，再动手。

## 两阶段工作法

**先出 spec，再开发。** 任何要构建的页面、报告、看板，或聊天里要排版的长内容，先完成下面的「呈现 spec」，过一遍红线自查，确认后才进入视觉与组件实现。不要边想边画，想清楚再画。

1. **Phase 1 - 呈现 spec**：按下面的检查项写出简短判断（内容清点、主次分级、呈现形式、取舍方式、状态完整性）。几句话即可，不是正式文档，但至少要写出「选了什么方案」和「排除了哪些方案、为什么排除」两部分——只写最终选择、不写排除理由，视为没做判断，退回重写。
2. **Phase 2 - 执行**：spec 确认后，视觉风格、布局节奏交给 `product-ui-design`；具体组件选型与实现交给 `shadcn-ui-patterns`；纯文字/markdown 场景（聊天回复、CLI 输出）按 spec 自己排版，不需要再走这两个 skill。

## Phase 1 检查项：写 spec 时问自己

这些是判断原则，不是写死的数字阈值。标准始终是「读者/用户当下这一次能不能自然地消化」，不是条数或字数本身——同样是 20 条，用户在找答案时 20 条太多，在对比价目表时 20 条可能刚好。

**自检法**：写完判断后，不要只凭感觉说"够清楚了"，反问一句——如果用户只看最先露出的那部分（扫一眼的前几秒、折叠前可见的那一段），他能不能已经抓到这段内容最重要的结论或选项？答不上来，说明 primary 层级选错了，回到第 3 条重新分级，不是加个"更多"按钮应付过去。

1. **内容是什么形态？** 先分类：同类多条记录、长文本/日志、多步骤流程、可切换的视角或状态、对比型数据、时间序列、原始结构化数据（JSON/表格）、混合体。形态决定后面怎么选呈现方式，不要跳过这一步直接动手画。
2. **用户此刻想干什么？** 浏览全貌、查找特定项、比较差异，还是按步骤往下走——同一批内容，目的不同，该露出的信息和该用的交互完全不同。没有目的判断，就只能套默认模板。
3. **哪些必须露出，哪些该收起来，哪些根本不用出现？** 把内容按三档分：当下决策/理解必须看到的（primary，常驻可见）、有需要才看的（secondary，折叠/展开/详情页/tooltip）、几乎不相关的（直接不显示，或挪到「更多」里）。不是每个字段都有资格常驻可见。
4. **量大时怎么取舍？** 常见手法：摘要在前+展开查看全部、分页、分组归类、按相关性排序后截断、抽样+「查看全部」入口。选哪种取决于内容形态和用户目的，不是固定按条数切，而是按「这一屏是否还能让人一眼抓住重点」判断。
5. **边界状态想过了吗？** 空状态、加载中、报错、极端量（0 条、1 条、远超常规的巨量）是否都设计了对应呈现，不能只有「数据刚好且数量适中」这一条路径。

## 内容形态 → 要问的问题（不是组件对照表）

下面按内容形态列出「该问什么问题」，不是「该用什么组件」——具体组件叫什么、长什么样，是 Phase 2 的事，这里只定交互形态和信息结构，不点组件名。同一形态在不同场景下，正确答案可能完全相反，问完问题才能决定，不要看到形态就条件反射套答案。

- 同类多条数据：用户是要扫视全貌找规律，还是逐条核对细节？前者倾向密集的聚合视图（如网格/摘要卡），后者倾向可逐项展开的结构（如明细表）——量大到一屏装不下时，再问该截断、分页还是分组。
- 长文本/日志/原始输出：用户需要的是结论还是过程？只需要结论就该把结论前置、细节收起来；需要追溯过程就该保留可展开的完整记录，但仍要有入口分层，不是整段直接铺开。
- 多步骤流程：步骤之间是否强依赖、必须按序完成？是，就该让用户一次只看当前步、知道进度；如果步骤彼此独立、可跳着填，堆在一屏反而更快，不必强行拆步骤。
- 可切换的视角或状态：用户需要同时对比多个状态，还是一次只关心一个？需要同时看就不该切换着藏起来；只关心当下一个，才该把其他状态收起来按需切换。
- 对比型数据：差异点是重点还是全量信息都重要？差异是重点就该让差异直接可见、相同项弱化；全量都重要就不该强行拆成对比格式丢失上下文。
- 时间序列/趋势：用户关心的是具体数值还是走势形状？关心走势就该让形状一眼可见；关心精确值就不能只给图不给数字。
- 原始 JSON/API 返回：先问哪些字段是这次交互真正用得上的，哪些是调试/溯源才用得上的——先挑字段再决定呈现，禁止原样转述成大段文字或无差别罗列全部字段。

## 创意呈现探索

内容形态 → 要问的问题只是起点，不要被它框死。好的呈现往往是为这一段内容量身设计的，不是从固定菜单里选一个最像的选项。下面每条创意方向都写成「想传达的信息关系」，不点具体组件名——落地成什么视觉形式交给 Phase 2，这里要确定的是「信息之间的关系该怎么被看出来」：

- 时间线/里程碑类内容：时间顺序和节点本身就是重点，该让「先后」和「停留点」被一眼看出来，而不是把时间降级成表格里普通一列
- 层级/从属关系：上下级关系是重点，该让用户能看出"这属于那"，并且能逐层收起/展开，而不是把所有层级拍平堆成同一级列表
- 情绪/结果反馈：好坏/轻重本身是重点信息，该靠视觉强弱（色彩、对比度、符号）直接传达，而不是只靠文字本身让用户自己去读
- 大量相似项：先看概览再看细节是常见路径，该让用户先扫到缩略信息，需要时再进入某一项的全部细节，而不是每项都展开到占满页面
- 流程/节奏感强的内容：推进感和当前位置是重点，该让用户随时知道"走到哪了、还有多少"，而不是靠纯文字描述步骤序号
- 密度不均的内容：信息密的地方和稀的地方本身就在传达"哪里重要"，该让排版的疏密呼应内容的疏密，而不是不管内容多少都套同一种固定间距

**唯一的约束**：每一个创意选择都要能回答「这个形式是不是让这段内容更容易被理解或决策，还是只是看起来花哨」。答不出前者，就退回朴素形式。创意服务内容，不能凌驾于内容之上。

## 红线：不允许的偷懒行为

- 原始数据/接口返回不做字段取舍，直接转成大段文字或无差别的全字段列表
- 内容量明显超出一次可消化范围，却原样整段甩出，没有任何摘要/分页/折叠
- spec 里分了 primary/secondary/不显示三档，但最终呈现没体现这个分级——比如三档内容最后还是同样字号、同样位置排成一排，分级判断等于白做
- 不管内容是什么形态，没问过「要问的问题」就直接套一种默认呈现
- 为了显得有创意而选择不匹配内容的复杂呈现，牺牲了可理解性

## 和其他 skill 的分工

`ui-content-triage` 产出「这堆内容该怎么呈现」的判断和简短 spec；`product-ui-design` 在此基础上定具体的视觉风格与布局节奏；`shadcn-ui-patterns` 负责把定下来的呈现方式用具体组件实现出来。三者按顺序执行，不要跳过 Phase 1 直接进入视觉或组件阶段。
