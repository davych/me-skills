# UI 内容分级呈现

模型拿到内容后最常犯的两类错：一是不判断就渲染——列表再长也全列出来，API 原始返回直接转成大段文字，所有字段同等字号铺开；二是矫枉过正——为了显得有取舍，把用户要的东西折叠、截断到找不到。本 skill 要求先判断，再动手。

## 何时用、用多重

- **跳过**：一屏能看完、只有一个层级、用户目的明确的内容（短回答、几条要点）。
- **轻量档**：聊天回复、CLI 输出等纯文字场景，内容偏长或有层级时，按下面的检查项在心里过一遍再排版，**不把 spec 输出给用户**。
- **完整档**：要构建页面、报告、看板，或内容明显超出一次可消化范围时，先写出呈现 spec，再进入实现。

## 两阶段工作法

1. **Phase 1 - 呈现 spec**：按检查项判断，完整档按下方模板写出。自检通过即可进入 Phase 2，不需要停下等用户确认；只有当用户目的无法推断、且不同目的会导向完全不同的方案时，才先问用户。
2. **Phase 2 - 执行与回检**：视觉风格与布局交给 `product-ui-design`；组件实现交给项目使用的组件层（shadcn 项目用 `shadcn-ui-patterns`，纯 HTML 报告等按对应 skill 或项目惯例）。spec 里的 primary/secondary/不显示分级是下游的硬约束：下游决定视觉表达，不重新分级。实现完成后对照 spec 回检，见末尾「回检」。

### spec 模板（完整档）

```
形态：…            目的：浏览 / 查找 / 比较 / 按步完成（推断依据：…）
primary：…         secondary：…          不显示：…
量大处理：…（总量与当前位置如何标示）
边界状态：空 / 加载 / 错误 / 部分失败 / 过期刷新 / 极端量 —— 各一句
备选：最有竞争力的一个替代方案，及没选它的原因
```

备选只写一个真实可行、认真考虑过的方案。不要为满足格式编造明显不合适的方案再否掉。

## Phase 1 检查项

这些是判断原则，不是写死的数字阈值。标准始终是「用户当下这一次能不能自然地消化」——同样是 20 条，找答案时太多，对比价目表时可能刚好。

1. **内容是什么形态？** 同类多条记录、长文本/日志、多步骤流程、可切换的视角或状态、对比型数据、时间序列、层级关系、原始结构化数据（JSON/表格）、混合体。形态决定后面怎么选，不要跳过。
2. **用户此刻想干什么？** 浏览全貌、查找特定项、比较差异，还是按步骤往下走。同一批内容，目的不同，该露出的信息和交互完全不同。推断不出时，默认按「先概览、可下钻」设计，并保证内容可被查找。
3. **哪些露出、哪些收起、哪些不出现？** primary（当下决策/理解必须看到，常驻可见）、secondary（有需要才看：折叠、详情、tooltip）、不显示（几乎不相关）。不是每个字段都有资格常驻可见；但报错、警告、不可逆后果永远不能降到 secondary。
4. **量大时怎么取舍？** 摘要在前+查看全部、分页、分组、按相关性排序后截断、抽样+入口。按「这一屏还能不能一眼抓住重点」判断，不按固定条数切。
5. **边界状态想过了吗？** 空状态、加载中、报错、部分失败（如 10 条里 2 条加载失败）、数据过期/刷新中、极端量（0 条、1 条、远超常规的巨量）。不能只设计「数据刚好且数量适中」这一条路径。

**自检**：写完后反问——用户只看最先露出的部分（扫一眼的前几秒、折叠前可见的那段），能不能抓到最重要的结论或选项？答不上来，说明 primary 选错了，回到第 3 条重新分级，而不是加个「更多」按钮应付。

## 按形态：要问的问题与要让人看出的关系

这里只定交互形态和信息结构，不点组件名——组件是 Phase 2 的事。同一形态在不同场景下答案可能相反，问完问题再决定。

- **同类多条数据**：扫视找规律，还是逐条核对？前者倾向密集的聚合视图，后者倾向可逐项展开的明细；量大时先让人扫到缩略信息，需要时再进入单项全部细节，而不是每项都展开占满页面。
- **长文本/日志/原始输出**：要结论还是过程？要结论就结论前置、细节收起；要追溯就保留完整记录，但仍要分层入口，不整段铺开。
- **多步骤流程**：步骤是否强依赖、必须按序？是，就一次只看当前步，并随时可见「走到哪了、还剩多少」；步骤独立可跳着填，就堆在一屏，不必强拆。
- **可切换的视角或状态**：需要同时对比多个状态就不该切换着藏起来；一次只关心一个，才收起其他按需切换。
- **对比型数据**：差异是重点就让差异直接可见、相同项弱化；全量都重要就不要强行拆成对比格式丢上下文。
- **时间序列/里程碑**：关心走势就让形状一眼可见，关心精确值就不能只给图不给数；时间顺序本身是重点时，让「先后」和「停留点」被看出来，而不是把时间降级成表格里普通一列。
- **层级/从属关系**：让人看出「这属于那」，并能逐层收起/展开，而不是拍平成同一级列表。
- **结果/情绪反馈**：好坏轻重本身就是信息，靠视觉强弱（色彩、对比度、符号）直接传达，不只靠文字让人自己读。
- **原始 JSON/API 返回**：先挑出这次交互真正用得上的字段，调试/溯源字段收起或不显示，禁止原样转述成大段文字或罗列全部字段。
- **混合体**：先按块拆开，每块按自身形态单独分级，再决定块与块之间的先后与主次。整体的疏密应呼应内容的疏密——信息密处给空间，稀处收紧，不套统一间距。

**创意约束**：可以为这段内容量身设计呈现，不必从上面挑最像的一条。但每个选择都要能回答「它是让内容更容易被理解或决策，还是只是看起来花哨」。答不出前者，退回朴素形式。

## 红线

露太多：
- 原始数据/接口返回不做字段取舍，直接转成大段文字或全字段列表
- 内容明显超出一次可消化范围，却原样整段甩出，没有摘要/分页/折叠
- 没问过「要问的问题」就直接套一种默认呈现

藏太多：
- 用户明确要「全部 / 完整」时仍截断或摘要
- 截断、分页、抽样时不标明总量和当前位置（如「显示 10 / 230」），或没有查看全部的入口；按相关性截断却不说明排序依据
- 报错、警告、不可逆后果被收进折叠或 secondary
- 用户目的是查找，却把内容折叠到无法搜索的位置，且不提供搜索/筛选

形式问题：
- spec 分了三档，最终呈现却没体现——同样字号、同样位置排成一排
- 为了显得有创意选择不匹配内容的复杂呈现，牺牲可理解性

## 回检（Phase 2 完成后）

对照 spec 逐项确认：primary 在首屏/折叠前可见；secondary 确实被弱化或收起，且有入口；「不显示」的内容没有混进来；spec 里列出的边界状态都有对应呈现；以上红线一条都没有触犯。
